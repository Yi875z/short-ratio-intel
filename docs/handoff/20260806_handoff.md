## 実行コマンドと結果

```
pytest                                    # 全119件パス（既存72件 + 新規47件）/ 9秒
python -m scripts.backfill_us_short_flow --days 250   # ローカルSQLiteへ実行
```

バックフィル実測: **249営業日 / 24銘柄 / 5,976行**（2025-08-08 〜 2026-08-05）。日足も5,976行。
再投入の冪等性を実データで確認（3日分72件を再upsert → 行数 5,976 のまま増えず）。

判定できた行の割合: z20 = 5,592 / 5,976、z60 = 4,824 / 5,976、CLV = 5,976 / 5,976。
序盤のサンプル不足期間は補間せず欠損のまま残している（QCルール6）。

最新日 2026-08-05 の実測例（**すべて候補であり断定ではない**）:

| ticker | ratio | z20 | z60 | pct60 |
|---|---|---|---|---|
| SPY | 68.2% | +2.82 | +2.17 | 98.3 |
| AMD | 62.6% | +2.08 | +2.24 | 98.3 |
| SMH | 43.1% | **−2.93** | −2.21 | 0.0 |

SPY 68% / QQQ 75% という高水準が常態である一方 SMH は 43% で z20 −2.93 という事実は、
「50%超え＝弱気」という絶対閾値判定が無意味であることの実データによる裏付けになっている。
なお ETF（SMH）側のショート比率が低位で個別（AMD等）が高位という並びは、
v2仕様の言う「個別選別型」の乖離パターンに見えるが、**判定は US-P2 のバスケット集計実装後**とする。

## ⚠️ 未完了・要対応（最重要）

**Supabase の新テーブルに RLS を有効化すること。**
`Base.metadata.create_all()` により、main へ push 後の最初の GitHub Actions 実行または
Streamlit Cloud 起動の時点で `us_short_volume_daily` / `us_market_daily` が
**RLS 無効のまま** Supabase に自動生成される。生成後すみやかに
`docs/migrations/2026-08-06_enable_rls_us_tables.sql` を SQL Editor で実行すること。
アプリは直接Postgres接続（所有者ロール）のため RLS を有効化しても壊れない。ポリシー追加は不要。

**本番Supabaseへのバックフィルは未実施。** ローカルSQLite（`data/us_flow_local_test.db`）でのみ検証した。
本番投入は人間の承認が必要な操作（固定ルール6）のため意図的に保留している。
実行する場合は `DATABASE_URL` を設定した状態で同じコマンドを叩く。
ただし現在の upsert は1行ずつ SELECT + INSERT するため、5,976行では Supabase 相手に時間がかかる見込み。
US-P2 で日次実行（1日あたり24行）に移れば問題にならないが、初回バックフィルのみバルク化を検討してもよい。

**未push。** PROJECT_RULES に従い、明示指示があるまでコミットのみで保留している。
