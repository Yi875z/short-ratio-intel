## レビュー総評（現状評価）

強み: 入力材料の多層化（ハウスビュー→イベントカレンダー→機関フロー→ライブ気配→RSSニュース→
テーマ履歴）は2026-05-30改修方針をほぼ完遂しており、品質チェック→改善メモ→再生成のループ、
lint（過剰断定・未確認断定検出）、ナレッジ鮮度表示まで揃っている。構造は健全。

残る欠落は大きく3系統:
1. **検証ループ不在** — レポートはレジーム判定・テーマ・シグナルを毎日出すが、翌日答え合わせをする
   仕組みがなく、的中率も自己校正材料も存在しない。
2. **価格文脈の欠落** — 業種別の空売り比率はあるが業種別騰落率がなく、「比率上昇×株価上昇=踏み上げ」
   「比率上昇×株価下落=方向性売り」という需給読みの基本突合ができていない。
   同様にオプション建玉・IV・日経VIの実データがなく、ナレッジ03(GEX)が毎回「未確認」で空転している。
3. **配信の欠落** — 毎日19時に生成されるのに、結論はアプリを開かないと読めない
  （Slack通知は文字数のみ）。

## フェーズ2（解釈力の本丸）

### 2-1. 業種別騰落率との4象限突合 【最重要】
- 現状: AIは業種別空売り比率の水準・前日比だけを見て解釈しており、株価反応との突合ができない。
  このため「高空売り=弱気」側に解釈が寄りやすい（踏み上げ・買い吸収の識別が不可能）。
- 変更:
  1. （要調査）東証33業種別指数の日次騰落率の取得元を確定する。第一候補は
     stock-marketdata.com（CLAUDE.md 市場データ取得元メモ参照）、次点は nikkei225jp.com の
     系列群。取得可否と保存・再利用可否を先に確認してから実装する（PROJECT_RULES 2章）。
  2. 新モジュール `src/macro_context/sector_price.py` を作り、業種別「前日騰落率」を取得。
     fail-soft（取得失敗時は従来動作）。
  3. `build_user_prompt()` の業種別テーブルに騰落率列を追加し、解釈ルールに4象限を明記:
     比率上昇×株価上昇=空売りが吸収されている（踏み上げ・押し目買い優勢の可能性）/
     比率上昇×株価下落=方向性売り優勢 / 比率低下×株価上昇=ショートカバー主導の可能性 /
     比率低下×株価下落=売り圧力後退でも買い不在。いずれも断定せず条件付き。
  4. スキーマ変更はしない（既存 `interpretation` / `pro_intent` 内で言及させる。最小差分）。
- 受け入れ基準: プロンプトに騰落率が入り、レポート本文が象限の言葉で業種を説明する。
  データ取得元・列名の仕様は実物確認の上で `docs/` に記録。pytest 緑＋新規テスト追加。

### 2-2. 先物・オプション建玉（JPX_Analysis_System）との突合

### 2-3. テーマ採点の鮮度減衰（中東バイアスの根治）
- 現状: `theme_detector.detect_market_themes()` の `news_score = min(len(keyword_hits), 3)` は
  当日ヘッドラインにキーワードが載り続ける限り満点が続き、慢性テーマ（中東・原油）が
  主テーマ候補に居座る。継続シグナル除外（第3弾改修）では news_score 自体は減衰しない。
- 変更: テーマごとに「主テーマ候補として連続した日数」を `market_theme_snapshots` 履歴から数え、
  N日（初期値5営業日）以上連続していて、かつ当日の keyword_hits が前日から増えていない場合は
  news_score を減衰（×0.5等）する。急変（ヒット数増・新規シグナル）があれば減衰しない。
  閾値は `config/signal_thresholds.py` か `config/settings.py` の定数にして調整可能にする。
- 受け入れ基準: 新規テストで「5日連続・ヒット数横ばいのテーマはスコアが下がり、
  ヒット数が増えた日は下がらない」ことを確認。既存テスト緑。

## フェーズ3（自己改善ループ・プロンプト整理）

### 3-1. 翌営業日検証・的中トラッカー
- 目的: レポートの `regime`・新規シグナル・主テーマを翌営業日の実際の市場
  （日経/TOPIX/該当業種の騰落。2-1のデータを流用）と突合し、的中/不一致を記録する。
- 変更: 日次パイプラインに検証ステップを追加し、結果をDBに保存。ダッシュボードに
  「先読みの成績」履歴を表示。直近10件の判定サマリーを翌日以降のプロンプトに
  「自己校正メモ」として1ブロック注入する（07過去事例と同じ思想の自動版）。
- 注意: 「的中」は厳密化しすぎない（レジーム=方向一致の粗い判定でよい）。まずMVP。
- 受け入れ基準: 検証行がDBに増え、UIに履歴が出て、プロンプトに校正メモが入る。

### 3-2. ハウスビュー草案の自動生成（人間承認前提）
- 現状: ハウスビューは手書きのみで、14日で鮮度警告が出るが更新は億劫になりがち。
- 変更: ハウスビュー編集expanderに「直近1週間のデータから草案を生成」ボタンを追加。
  直近レポート・テーマ履歴・ライブ気配を材料に Gemini で草案を作り、**テキストエリアに
  流し込むだけ**（保存は人間が編集・確認してから。無人更新禁止ルールに適合）。
- 受け入れ基準: ボタンで草案が入り、保存フローは従来どおり人間操作。クォータ消費は
  ボタン押下時のみ（1リクエスト）。

### 3-3. システムプロンプトの再構成（重複排除・階層化）
- 現状: 指示が「Step0 / 分析の鉄則24項目 / ラベル分離 / JPX内訳 / シグナル履歴 / イベント /
  レジーム裁定 / テーマ判定 / ニュース数値 / ユーザープロンプト末尾の必須列挙 / スキーマ
  description」に分散し、同趣旨の指示が3箇所で重複している例がある（フィールド必須指示等）。
  flash系モデルは指示リストが長いほど個別遵守率が下がるため、整理の余地が大きい。
- 変更方針: (a) ハード制約（禁止事項・Step0・確度ラベル）/ (b) 解釈フレーム（JPX内訳・
  シグナル・イベント・レジーム・テーマ）/ (c) フィールド別指示（スキーマdescriptionに一本化し
  本文からは削除）の3層に再編成。**意味の変更はせず整理のみ**。
- 検証: 変更前後で同一日のレポートを生成し、品質パネルのスコアと欠落フィールド数
  （gemini_client の setdefault 発動数をログ化して数える）を比較。悪化したら差し戻す。
  プロンプト調整を3回書き直しても改善しなければ損切りする（PROJECT_RULES 4章）。

### 3-4. （検討）Gemini構造化出力 response_schema の併用
- 現状: スキーマJSONを本文貼付+`response_mime_type="application/json"`。モデルがフィールドを
  落とすため `_parse_response` に10個超の setdefault 補完がある。
- 変更案: `generation_config` に `response_schema`（Pydantic連携）を併用し欠落を減らす。
  **json-repair と setdefault の防御層は絶対に外さない**（PROJECT_RULES 5章の固定ルール）。
  スキーマが大きく response_schema が制限に当たる場合は見送り、本書に結果を追記。

## 実装時の共通注意（全フェーズ）

1. 公開リポである。Secrets・接続文字列・鍵をコード/ドキュメント/コミットに書かない。
   コミット前に秘密スキャンを行う。
2. Gemini Free Tier は 20 RPD。デバッグでの再生成連打は1日で枯渇する。プロンプト変更の検証は
   1〜2リクエストに絞り、ローカルでプロンプト文字列の目視確認を先に行う。
3. `gh workflow run` をループ・自動リトライで叩かない（単発のみ）。
4. 外部データ突合系（2-1, 2-2）は必ず fail-soft。新規接続が死んでも日次レポートを止めない。
5. DBカラム・外部テーブルのスキーマは実物確認。推測で実装しない。不明は「未確認」と明記。
6. push 後の動作確認は Streamlit Cloud の再デプロイ完了を待ってから（旧コンテナで生成された
   レポートを見て「反映されない」と誤認した前例あり）。
7. 各フェーズ完了時に `docs/handoff/YYYYMMDD_handoff.md` を残す（PROJECT_RULES 6章の書式）。
